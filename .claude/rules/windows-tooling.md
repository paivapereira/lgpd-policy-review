# Windows tooling

## Principle

In PowerShell 5.1 native (Windows corporate-restricted; no WSL
available), `Out-File -Encoding utf8` emits UTF-8 with BOM. For
commit messages, file content, and any text intended to be
interpreted as pure UTF-8, use
`[System.IO.File]::WriteAllText` with an explicit
`UTF8Encoding($false)`.

## Justification

Materialized in session #25 during commit message authoring.
`Out-File -Encoding utf8` injected a BOM, which propagated to
commit subjects and broke conventions. Fix: explicit no-BOM
encoder. Behavior is corrected in PS 7+ (where `utf8NoBOM` is
available), but the operating environment is PS 5.1.

## When to apply

- Writing commit messages from a file (multi-line commits or
  templated subjects).
- Writing any file whose downstream consumer is sensitive to
  BOM (git, parsers, CI tooling).
- Generally in this environment, prefer the explicit pattern
  rather than relying on `Out-File` defaults.

## How to apply

    $msg = "feat(scope): subject line`n`nBody paragraph here."
    [System.IO.File]::WriteAllText(
      "$PSScriptRoot\commit-msg.txt",
      $msg,
      [System.Text.UTF8Encoding]::new($false)
    )
    git commit -F .\commit-msg.txt
    Remove-Item .\commit-msg.txt

For single-line subjects, `git commit -m "..."` with the subject
inline avoids the temp file entirely and is preferred when the
subject fits.

## Commit message subjects: ASCII-fy when invoking git via bash HEREDOC

### Principle

When the git commit is invoked from a bash HEREDOC under PowerShell 5.1
(typical pattern for multi-line subjects or templated commit messages),
ASCII-fy the subject and body of the commit message: remove accents,
substitute em-dashes for plain hyphens. The file content being committed
preserves all accents — the rule applies only to the commit metadata.

### Justification

Materialized across sessions #28 (Provisão B) and #30 (PR #55 housekeeping).
The combination PS 5.1 + bash HEREDOC + UTF-8 has encoding alignment
fragility (console code page cp1252, bash UTF-8, git's own assumptions).
Risk: subject lands in git history with mojibake. Cost of mitigation:
trivial (ASCII subject); cost of regression: commit history with corrupted
characters, hard to fix retroactively.

Norm ADR-0001 Decision 3 (Brazilian Portuguese for user-facing outputs)
applies to file content — text that ends up in artefacts read by users,
banca, auditors. Commit messages are history metadata, not user-facing
output in the normative sense. Squash-merge collapses the internal commit
message into a subject auto-generated by GitHub UI from the PR title;
internal subjects have short shelf life in main history.

### How to apply

- PR title (via GitHub UI): preserves accents. Source-of-truth for squash
  subject in main.
- Internal commits pre-squash: ASCII subject and body. Example:
  `docs(canonical): sync semgrep-runner examples to bare convention`
  (not `sincroniza` or `convenção`).
- File content committed: full accents preserved per ADR-0001 Decision 3.
- `git commit -m "subject"` inline (single-line subjects) is preferred
  when the subject fits, avoiding HEREDOC entirely.

### Scope

Applies only to PowerShell 5.1 native environment. PowerShell 7+ with
`utf8NoBOM` resolves the encoding issue and may handle accented subjects
correctly — but the project environment is pinned PS 5.1.

## Reference

No direct Anthropic guidance — environment-specific to Windows
