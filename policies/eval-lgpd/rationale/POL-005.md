## 1. Identificação e propósito

**Identificador.** `POL-005`. Opaco, prefixo `POL-`, alocado conforme a regra
unidirecional de identidade do SCHEMA §4.1. O range 005+ foi escolhido para a
política de avaliação porque 001–004 já estão **semanticamente ocupados** pelo
pacote de fixtures do `check_applicability` (ver
`docs/eval/test-cases-proposal.md` §Numbering).

**Título.** Coleta de dados de identificação exige consentimento do titular.

**Tipo.** Cláusula substantive (`clause_type: substantive`) — prescreve um
`control` para a combinação `personal_data_categories × operation`, na forma do
SCHEMA §6.

**Função.** Materializa, na Política, a exigência do Art. 7º da LGPD de uma base
legal para o tratamento de dados pessoais comuns, especializada para a hipótese
de **consentimento** (Art. 7º, I) quando a operação é a **coleta** de dados de
**identificação** (POL-000 §2.1).

## 2. Base estatutária

**Art. 7º, I, da Lei nº 13.709/2018 (LGPD).** O tratamento de dados pessoais
somente pode ocorrer mediante o fornecimento de consentimento pelo titular. A
cláusula ancora-se na hipótese de consentimento como base legal exigível quando
nenhuma outra hipótese do Art. 7º for declarada para a coleta.

`statutory_reference` (YAML): `[{lei: LGPD, artigo: 7, inciso: 1}]` — paridade
direta com a âncora citada nesta seção.

## 3. Âmbito de aplicação (`applies_to`)

- `personal_data_categories: [dados_de_identificacao]` — classe funcional
  POL-000 §2.1 (`special_category: false`).
- `operation: [collection]` — única operação avaliável no MVP (ADR-0007 D1).

A cláusula governa, portanto, o ponto de **coleta** de atributos que nomeiam ou
rotulam diretamente o titular (nome, nome social, username, data de nascimento).

## 4. Controle prescrito (`control`) e requisito

`control: consent_required`. No motor MVP v0.1.0
(`src/mcp_servers/policy_reader/tools.py` `_verdict_for_control`), o controle
`consent_required` é avaliado por **igualdade exata** contra o token canônico
`consent` do vocabulário `lawful_basis`:

- `legal_basis == "consent"` → `compliant`;
- `legal_basis` ausente → `violation_candidate` (omissão), `contradicted_requirement: R1`;
- `legal_basis` presente porém ≠ `consent` → `violation_candidate` (valor não-canônico), `contradicted_requirement: R1`.

**R1** (paridade com o YAML): a coleta de dados de identificação exige o token
`consent` como base legal; ausência ou valor diverso configura tratamento sem a
base que a cláusula prescreve.

## 5. Exceção declarada (`exceptions`)

**E1.** A cláusula não incide quando a mesma coleta estiver amparada por outra
hipótese do Art. 7º (p.ex. execução de contrato, Art. 7º, V). **Limite de
modelagem MVP:** o motor avalia esta cláusula isoladamente e por token único
`consent` — ele **não** reconhece bases alternativas como conformes. Em uma
coleta de identificação legitimamente baseada em `contract_performance`, o motor
emitirá `violation_candidate` (falso positivo de conformidade). Essa
sobre-restrição é a motivação central do controle `lawful_basis_required`
proposto em **ADR-0015** e do caso de fronteira `B-FALSEPOS` no catálogo de
avaliação.

## 6. Papel na avaliação empírica

POL-005 é o veículo de três classes de caso do catálogo de avaliação:

1. **compliant** — coleta de identificação com `legal_basis: consent`.
2. **violation_candidate** — coleta de identificação sem base, ou com base ≠ `consent`.
3. **swap LGPD↔GDPR** — sob a Política LGPD, `consent` → `compliant`; sob o gêmeo
   GDPR, cujo vocabulário `lawful_basis` nomeia o consentimento como `consent_gdpr`,
   o **mesmo código** normaliza para `consent_gdpr`, que o motor (hardcode
   `== "consent"`) rejeita → `violation_candidate`. O veredito muda por **diferença
   de vocabulário de base legal**, não de código (ver `docs/eval/test-cases-proposal.md`).
